================================================================================
OVERVIEW
================================================================================

Exim's GnuTLS-backed SMTP server contains a heap use-after-free, reached when a
TLS session is torn down while a chunked body transfer - BDAT, from the
CHUNKING extension - is still in progress.  The per-session transfer buffer is
released and the session object destroyed while the reader callbacks bound to
that buffer stay installed and keep being dispatched, handing both released
objects back to the library.  Buffer, session handle and reader callbacks did
not share a lifetime.

Impact is heap corruption: up to 4096 attacker-supplied bytes decoded into a
freed allocation, once per refill for the rest of the declared chunk, in a
network-facing process parsing untrusted input.  A use-after-free read, an
expired-pointer dereference, and a confidentiality failure - the read path
silently continued reading the same TCP socket in clear - are reachable
alongside it.  Reachable pre-authentication on a stock build with a stock
configuration.

CWE: CWE-416, CWE-825, CWE-672

Affected variant: GnuTLS.  The OpenSSL backend is affected differently and far
less severely; see IMPACT AND CLASSIFICATION.

================================================================================
TECHNICAL DETAILS
================================================================================

Line references are to the tree as it stood before remediation.

--------------------------------------------------------------------------------
Root Cause
--------------------------------------------------------------------------------

Each server-side TLS session owns a 4096-byte transfer buffer, allocated
unconditionally at handshake (src/src/tls-gnu.c:3279; size at
src/src/tls.c:74).  store_free() is a real libc free(), not a pool release
(src/src/store.h:50, reaching free() at src/src/store.c:1251), so this is
genuine heap corruption.  tls_close() released both objects and left both
pointers in place:

    // src/src/tls-gnu.c:3989 and :3996
    gnutls_deinit(state->session);
    if (state->xfer_buffer) store_free(state->xfer_buffer);

Neither pointer was cleared and none of the four state fields was reset -
xfer_buffer_lwm, xfer_buffer_hwm, xfer_eof, xfer_error (217-218, 252-254) - so
the non-NULL test guarding the free was inert and the water marks still
described a released buffer.  Upstream had already annotated xfer_eof as never
set, and it never was: no code assigned it.  It was read, though - through the
shared macro (src/src/tls.c:479) by tls_feof() (528-530), the routine
receive_feof() dispatches to once a session is up (tls-gnu.c:3359) - so the
end-of-file channel could not report the end of the input on this backend.

Two properties make this reachable rather than theoretical.  tls_refill()
itself calls tls_close() on end of transmission (654), so the releasing agent
and the next consumer are one call chain.  And the read path did not fail
closed: the read-timeout branch (644-649) and the genuine-error branch
(660-666) each set xfer_error, but the zero-byte end-of-transmission branch
(651-656) - the one that releases both objects - did not, so the byte reader
fell through to smtp_getc() (4021-4023) and the teardown was invisible to its
caller, which read on.

Re-entering teardown on the same context does not release twice: the entry
guard at 3949 tests active.sock, which 3990 sets to -1 before the free, so the
second entry returns immediately.  On that path the residual exposure is
dangling-pointer hygiene alone.  That bound holds for same-context re-entry
only; the ATRN state transplant escapes it, and is the fifth unsafe path below.

--------------------------------------------------------------------------------
Unsafe Paths
--------------------------------------------------------------------------------

1.  Use-after-free write through the library.  The next refill passes both
    released objects to GnuTLS in one call - up to 4096 decoded bytes into the
    freed allocation, the destroyed handle dereferenced on the way, repeating
    once per refill while the chunk is unfinished:

    // src/src/tls-gnu.c:625-626
    inbytes = gnutls_record_recv(state->session, state->xfer_buffer,
      MIN(ssl_xfer_buffer_size, lim));

2.  Use-after-free read, no library involved.  The one-byte push-back described
    next does not only write into the released block; it also leaves the
    low-water mark below the high-water mark, so the very next byte read takes
    the buffered-data fast path and indexes the released block directly:

    // src/src/tls-gnu.c:4027
    return state->xfer_buffer[state->xfer_buffer_lwm++];

    The two marks are equal at the moment of release - a refill is entered only
    when they are equal, and the end-of-transmission branch returns before
    assigning them - so this read follows the push-back rather than arising on
    its own.  The buffer reader can leave the marks unequal by handing back less
    than it holds, but not across a teardown, for the same reason.

3.  One-byte use-after-free write in shared code, reached when header parsing
    pushes bytes back through the chunked-body ungetc.  The only guard was an
    underflow test that a stale positive low-water mark defeats; under the
    USE_GNUTLS macro aliases (src/src/tls.c:476-480) the symbol is the server
    context's buffer:

    // src/src/tls.c:510
    ssl_xfer_buffer[--ssl_xfer_buffer_lwm] = ch;

4.  Expired-pointer dereference: the pending-data check and the raw read entry
    point both used the destroyed session handle.

5.  Two contexts naming one buffer and one session, on the ATRN state
    transplant.  The provider direction, which turns the inbound context into
    the outbound one, copied the whole server context - buffer pointer and
    session handle with it - allocated no replacement, and left the server
    context still naming both:

    // src/src/tls-gnu.c:4414
    *state = state_server;

    The customer direction (4446) duplicated the session handle the same way,
    allocating a fresh buffer (4451) but not detaching the outbound context
    from the session.  Whichever of the two contexts was closed first released
    objects the other still named, and what stops same-context re-entry does
    not stop this: each direction zeroes the support block it moved out of
    (4425 and 4458), a zeroed active.sock is 0, and the test at 3949 admits
    anything that is not negative.  A second release of the same buffer was
    reachable here.  That test has to stay "not negative" rather than "not
    zero", because both transplant callers legitimately pass descriptor 0
    (src/src/atrn.c:59 and :139).

The DKIM verification feed sits on this same path (src/src/tls-gnu.c:668), so
the released buffer was also the one offered to signature verification.

--------------------------------------------------------------------------------
Stale Reader Dispatch
--------------------------------------------------------------------------------

Teardown reset only the top-level receive_* reader vector, and only for the
server case (3978-3987) - never the saved lwr_receive_* vector, which is the
one the BDAT layer in src/src/smtp_in.c dispatches through.  That was
insufficient three times over.  The chunked-body readers are called directly
from src/src/receive.c and go through the saved vector.  The pop ending a chunk
copies that vector back over the top-level one (src/src/smtp_in.c:953), undoing
the reset and promoting the stale readers to primary for all that follows,
chunked or not.  A defensive re-pop when the next message starts on the same
connection (3845) does the same again.  All four dispatch sites make an
unguarded indirect call (763, 887, 900, 969), which is why the saved vector
must be corrected, not emptied.

================================================================================
REACHABILITY AND EXPLOITATION
================================================================================

Both preconditions are on by default - chunking_advertise_hosts and
tls_advertise_hosts are each US"*" (src/src/globals.c:577 and :92) - and each
is advertised in the EHLO response gated only by a host check: CHUNKING at
src/src/smtp_in.c:4420, emitted at 4423; STARTTLS at 4434-4435, emitted at
4438.  Neither gate involves authentication.  The trigger is an ordinary SMTP
dialogue:

    connect, EHLO, STARTTLS, EHLO, MAIL FROM, RCPT TO,
    BDAT <n>           sending fewer than <n> bytes of body,
    TLS close_notify   while leaving the TCP socket open

The declared chunk is left unfinished, so the server comes back for more body
after the session it was reading through has been destroyed.  No credentials
are required, no configuration change is required, there is no race window to
win and no prior information leak is needed.  The attacker controls both the
moment of teardown and the content then decoded into the released allocation.
The daemon forks one process per accepted connection, so this is
pre-authentication remote heap corruption in a process parsing untrusted input.
A context an outbound delivery makes for itself is unaffected:
tls_client_start() (3619-3620) never allocates a transfer buffer, so such a
context holds a NULL one and none of the above reaches it.  The exception is the
outbound context the ATRN transplant builds by copying the server's, which does
name the server's buffer and session; that is the fifth unsafe path above.

================================================================================
AFFECTED VERSIONS
================================================================================

Present in the 4.100 development tree and, on the evidence of the project's own
release record, in all preceding releases that shipped the GnuTLS backend with
CHUNKING support.  The basis is that before the entry recording this fix,
doc/doc-txt/ChangeLog held no entry referencing the transfer buffer, tls_close()
or gnutls_record_recv(), its only mention of tls-gnu.c at all being an unrelated
DH_BITS change from a much earlier era: the allocate-and-free asymmetry between
the two TLS backends is long-standing, not a recent regression.  The entry
recording this fix is now the first such reference.

The exact earliest affected release cannot be established without access to
external project history, which was not available when this report was written.
That is a stated bound on this analysis; the claim above is deliberately not
narrowed further.

================================================================================
IMPACT AND CLASSIFICATION
================================================================================

CWE: CWE-416, CWE-825, CWE-672

Anchors taken from the standing CWE catalogue; the catalogue pages themselves
were not retrieved and are not quoted.

-   CWE-416, Use After Free - primary, in both its write and read form.

-   CWE-825, Expired Pointer Dereference - the destroyed session handle, still
    reachable from the read routines.

-   CWE-672, Operation on a Resource after Expiration or Release - the
    transfer-state indices, never invalidated and so still describing released
    memory.

Consequentially this is heap corruption, up to 4096 attacker-supplied bytes
being writable into a freed allocation.  Availability impact is immediate;
integrity and confidentiality impact follow from an attacker-influenced write
into released heap memory in a network-facing process.  The adjacent
confidentiality concern is the silent continuation of reading in clear on a
socket whose negotiated session had been destroyed.

CWE: CWE-476

On the OpenSSL backend the buffer use-after-free does not arise, that backend
never releasing its transfer buffer.  Its equivalent stale-reader path instead
reaches a read call with a NULL session - a NULL-pointer dereference, so a
crash of the one forked per-connection process rather than heap corruption.
The remediation below closes that path too, and the parts of it that do so are
shared: the teardown decision is taken in the chunked-body layer, and the gate
that holds a retired input closed sits in the refill the plain readers go
through, so it governs the byte reader and the buffer reader alike whichever
backend installed them.  The OpenSSL backend is edited only to reach those
shared parts - the decision is called from the end-of-transmission branch of
that backend's refill, and the saved reader vector is invalidated at its
teardown - its own readers being left as they were.  Closing that backend's
exposure is a consequence of this fix rather than its subject.

Any severity characterisation here is a code-derived assessment, not verified
against NVD, MITRE or any vendor advisory.

================================================================================
REMEDIATION
================================================================================

Install a build containing the fix; no fixed release number is stated in this
report.  Buffer, session handle and the reader callbacks operating on both are
given a single, jointly enforced lifetime, and the consumers are guarded so no
residual path can act on a released object.

-   At release the owning pointers are cleared - the session pointer
    immediately after gnutls_deinit(), the transfer-buffer pointer immediately
    after store_free() - the water marks are zeroed, and the end-of-file and
    error latches are set.  All of that is unconditional, for every teardown of
    a server session, so a reader that still reaches this state finds it
    finished rather than half-described, whatever the dialogue was doing at the
    time.  It also gives xfer_eof a value, which nothing had ever done - the
    routine that reads it could until now only ever report this input as
    unfinished.  What makes the end of the input observable after a teardown is
    not that flag, though: teardown points the end-of-file check at the plain
    reader's own record, which the retirement described below sets.

-   Before the buffer is released, the saved lower-layer reader vector no
    longer refers to the TLS readers.  It is re-pointed at the plain readers -
    the same ones the teardown installs as the top-level vector - and only when
    a vector has actually been pushed, so the "nothing pushed" sentinel that
    push and pop both key on keeps its meaning.  That vector can no longer
    dispatch a TLS reader: not directly, not by promotion back to primary, and
    not by a re-pop on a later message.

-   What becomes of the socket is settled on the read path, before the session
    is released and before anything is pointed back at that socket, and it has
    exactly two outcomes.  If a transaction is in progress - a sender or
    recipients already accepted, or a chunked body being received - the input is
    retired: it is recorded as ended, anything buffered for it is discarded, the
    refill both plain readers go through refuses to read the socket again, and
    the end of the input becomes observable through the feof channel.  The
    message in progress therefore fails and no further command is taken from
    that connection.

-   Otherwise the peer ended the session between commands.  That is a handoff
    this server documents and performs itself, so the connection does continue
    in clear - but as an explicit downgrade, and as a plain connection and
    nothing more.  Every piece of state the ended session conferred is dropped
    with it: the authenticated sender and identity established under it, and the
    whole recorded TLS status.  STARTTLS is offered again, as on any plain
    connection.

-   The latches cannot be inherited.  Both of the sites that allocate a transfer
    buffer initialise the transfer state for the session they are starting - the
    server handshake and the state transplant an ATRN customer child takes over
    - so no later session begins life holding an earlier teardown's end-of-file
    or error.  The server context is not re-zeroed between successive TLS
    sessions on one TCP connection, and its stale water marks were already being
    inherited into a fresh buffer before this change, so these resets are part
    of the fix rather than optional hardening.  Teardown likewise clears
    the flag recording that peer details have been taken: without that, a second
    session on one connection inherited the first one's reported version, cipher
    and certificate status instead of computing its own.

-   The consumers - refill, the byte and buffer readers, the cached-data feed,
    the pending-data check, and the read and write entry points - test for a
    released session or buffer before use and answer from that test rather than
    touching it, in whatever form each interface requires: end-of-file, no
    data, or an error.  The one-byte write in shared code is guarded the same
    way, in a form correct for both TLS backends.

-   The ATRN state-transplant paths no longer leave two contexts naming the
    same session and buffer.  Each hands sole ownership to the context that
    will go on to close it and drops the other's reference, so the second
    release described in the fifth unsafe path cannot happen; the descriptor
    test stays "not negative", so a transplant onto descriptor 0 keeps working.

Changes are confined to the TLS transfer-buffer lifetime logic and the
chunked-body handling: src/src/tls-gnu.c, src/src/tls.c, src/src/smtp_in.c,
three added declarations in src/src/functions.h, and in src/src/tls-openssl.c
the two calls by which that backend reaches the shared teardown decision and
the shared reader reset.  What does not change: no public
API and no ABI; no change to the SMTP protocol on the wire; no change to the
spool file format; no new configuration option and no change to any existing
option or default value; no change to the chunking state machine or any of its
transitions.

The one workaround is a compensating control, not a fix: restricting
chunking_advertise_hosts so CHUNKING is not advertised removes the trigger, but
it requires an explicit configuration action, the option's default value being
"*", and it changes configuration semantics, withdraws a standards-defined SMTP
capability from every peer, and leaves the defect in the code for anyone who
restores the advertisement.  For the project's handling of security releases
and vendor backports - latest released version supported, vendors helped to
backport, exim-VERSION+fixes branches recommended, some issues addressed by a
patch release carrying just the fix - see <https://wiki.exim.org/EximSecurity>
and <https://wiki.exim.org/SecurityReleaseProcess>.

--------------------------------------------------------------------------------
Behavioural Change
--------------------------------------------------------------------------------

Two behaviours change deliberately, and both are disclosed here rather than
left to be discovered.

The first.  A peer that tears down TLS in the middle of a transaction while
holding the TCP socket open previously had its subsequent traffic read in clear
on that socket, as though it were a continuation of the encrypted session.  The
read path now fails closed instead: that traffic is not read, the message in
progress fails, and no further SMTP command is accepted on the connection.

This is correct hardening, not breakage - reading a socket in clear after the
negotiated session has been destroyed voids the confidentiality guarantee the
peer negotiated, and it was also the loop that repeatedly re-entered released
memory.  For precision: the server still emits a terminal failure response
before closing, and because the session is already gone that response goes out
in clear.  The claim is about the read path, and about no further command being
accepted - not that nothing whatever is transmitted after teardown.

Peers that do not shut a session down while intending to carry on reading the
socket reach none of this.  In particular the handoff Exim's own SMTP transport
performs for a host matched by hosts_noproxy_tls - shutting the TLS session down
and sending a fresh EHLO in clear on the same socket, to learn whether the
socket may be passed to the next delivery process - happens between messages,
not during one, so it is not this case; it is the second one below, and it keeps
working.
The regression suite holds the fix to that: tests 1157, 3451 and 3461 take
several messages over one connection with the session ended between them, and
they pass against their unchanged saved references.

The second.  A peer that ends the session cleanly between commands is a
different case and is treated differently, because that is a handoff this
server documents and performs itself when it passes a connection to another
process.  Such a connection still continues in clear - but now as a plain
connection and nothing more.  Previously the recorded session outlived its own
destruction: a sender authenticated under TLS, the identity that authentication
established, and the whole reported TLS status - version, cipher, certificate
verification result - stayed attached to the connection and were applied to,
and logged for, messages accepted in clear afterwards.  That state is now
dropped when the session ends, and STARTTLS is offered again.  A peer that
relied, knowingly or not, on authentication or TLS status carrying across a
session teardown must authenticate again, or negotiate again, on what is left
of the connection.

--------------------------------------------------------------------------------
Verification
--------------------------------------------------------------------------------

Remediation is checked two ways: with a sanitizer-instrumented build driven by a
reproducer combining a partial BDAT chunk with a TLS shutdown, and with the
project's regression suite.  The negative control is mandatory and its order
matters: the reproducer must be shown to fail on the unremediated tree first,
and to pass only after the fix is applied.  One that passes in both states is a
defective test, not evidence of a fix.  The pass criterion is the absence of any
sanitizer report, not merely the absence of a crash, since an uninstrumented
build can survive a use-after-free write silently.

Two of the unsafe paths above are directly observable this way, and both were
observed.  On the unremediated tree the reproducer yields a heap-use-after-free
WRITE of size 1 in tls_ungetc at src/src/tls.c:510, and a heap-use-after-free
READ of size 1 in tls_getc at src/src/tls-gnu.c:4027 - both into the same
released allocation, both reports naming its release in tls_close
(src/src/tls-gnu.c:3996, reached from tls_refill at :654) and its allocation in
tls_server_start (:3279).  Because the read becomes reachable only after the
write has moved the low-water mark, the sanitizer has to be built and run so
that it continues past the first report; stopping at the first one hides the
second.  After the fix neither report appears, and the connection ends rather
than the partial body being accepted.

One limitation belongs here rather than being left unsaid.  The first of the
unsafe paths - the up-to-4096-byte store GnuTLS itself performs into the
released buffer - is not visible to the sanitizer.  The allocation written into
is Exim's, but the write is executed inside the library, which is not
instrumented.  That path is closed by the same change, and is argued from the
code rather than from a sanitizer report; no report should be claimed for it.
The other two paths above - the expired session handle, and the second release
on the ATRN transplant - are not what this reproducer drives, and are argued
from the code in the same way; no sanitizer report is claimed for them either.

What that produced.  Under the sanitizer, the unremediated tree reported
heap-use-after-free for both variants driven at it: the one-byte write through
the shared unget path, and the direct read of the released buffer.  On the
remediated tree, built from the sources this report describes, both variants run
to completion with no sanitizer report of any kind, the connection ending in a
terminal failure response instead.

The reproducer added to the suite behaves the same way round.  It fails on the
unremediated tree - both on the tree this work started from and on an
intermediate one that latched the transfer state only conditionally - and passes
on the remediated tree.  No run of it emits either the chunked-body double-push
or the double-pop diagnostic; nor does any other run made for this work.

The regression witnesses behave as they did before the change: chunked reception
and transmission, chunked transfers under TLS, the state-transplant paths, the
interaction with message signature verification both with and without TLS, early
pipelining and per-recipient data all pass, apart from a few that already failed
on the unremediated tree for reasons unrelated to this defect and fail
identically after it.  The whole automatic range of the suite was then run on
both trees and the failing sets compared: the set that fails consistently is the
same on each, and the remediated tree introduces no failure of its own.  The
GnuTLS category the reproducer joins passes in full.  The other backend's own
category, and the shared TLS category, were run from a build of that backend and
are unchanged between the two trees as well.

One caveat for anyone reproducing this.  A handful of tests in the suite turn on
wall-clock spacing, on kernel fast-open state, or on generated file names, and
so pass or fail according to how loaded the machine is rather than according to
what the code does.  Each full run turned up one or two of them, and never the
same ones - the run on the unremediated tree had its own - which is why the
comparison above rests on repeated runs and on the set that fails consistently,
and not on any single run.

Regression runs drive the harness non-interactively and never rewrite its saved
reference files, the option that would rewrite them being excluded precisely
because it would mask the regression the run exists to detect.  The binary
handed to the harness is used at both ends of each scenario, so a scenario that
has to be served by one particular TLS backend is run by handing the harness a
build of that backend and passing no backend-selecting option: that option is
for cross-library testing and puts the other build on the server side, which
would leave such a scenario served by the wrong one.

    cd test
    ./runtest ../src/build-Linux-x86_64/exim --continue --range 2000 2099

The binary given there is the one that serves the connection, so it also decides
which backend is under test: a GnuTLS test has to be run with a GnuTLS build.

Sanitizer runs are driven outside the harness and against a build that is not
installed setuid, the harness installing a setuid copy of the binary and that
not coexisting with the sanitizer.
