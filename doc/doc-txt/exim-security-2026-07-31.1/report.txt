================================================================================
OVERVIEW
================================================================================

Exim's GnuTLS-backed SMTP server contains a heap use-after-free, reached when a
TLS session is torn down while a chunked body transfer - BDAT, from the
CHUNKING extension - is still in progress: the per-session transfer buffer is
released and the session object destroyed while the reader callbacks bound to
that buffer stay installed and keep being dispatched. Impact is heap corruption
in a network-facing process parsing untrusted input, reachable
pre-authentication on a stock build and configuration.

================================================================================
TECHNICAL DETAILS
================================================================================

Line references are to the tree before remediation. Each server-side TLS
session owns a 4096-byte transfer buffer, allocated at handshake
(src/src/tls-gnu.c:3279) and released with a real libc free(). tls_close()
released both objects and left both pointers in place:

    gnutls_deinit(state->session);                            /* 3989 */
    if (state->xfer_buffer) store_free(state->xfer_buffer);   /* 3996 */

Neither pointer was cleared and none of xfer_buffer_lwm, xfer_buffer_hwm,
xfer_eof, xfer_error was reset (217-218, 252-254), so the non-NULL test
guarding the free was inert, the water marks still described a released buffer,
and xfer_eof was never assigned at all. Two properties make this reachable
rather than theoretical: tls_refill() calls tls_close() itself on end of
transmission (654), so the releasing agent and the next consumer are one call
chain, and that branch left xfer_error unset, so the byte reader fell through
to smtp_getc() (4021-4023) and the teardown was invisible to its caller.

Five unsafe paths follow: the next refill passing both released objects to
gnutls_record_recv() in one call (625-626), decoding up to 4096
attacker-supplied bytes into the freed allocation once per refill for the rest
of the chunk; a use-after-free read with no library involved at 4027; a
one-byte use-after-free write in shared code at src/src/tls.c:510, past a guard
a stale low-water mark defeats; the pending-data check and the raw read entry
point dereferencing the destroyed session handle; and the ATRN state transplant
leaving two contexts naming one object - the buffer and the session at 4414,
which allocates nothing, the session alone at 4446, which does allocate a fresh
buffer - so a second release was reachable.

Teardown reset only the top-level receive_* reader vector, and only for the
server case (3978-3987) - never the saved lwr_receive_* vector, the one the
BDAT layer in src/src/smtp_in.c dispatches through, at four sites, indirectly
and unguarded (763, 887, 900, 969). Those readers therefore went on being
called through it, and the pop ending a chunk copied it back over the top-level
one (smtp_in.c:953), promoting them to primary.

Separately, the one server context is reused for successive sessions on a
single TCP connection and is never re-zeroed after process start, while several
fields recording what a session negotiated are only ever set. A session
following another on that connection could therefore report its predecessor's
server name, cipher suite and certificate as its own.

================================================================================
REACHABILITY, AFFECTED VERSIONS AND IMPACT
================================================================================

Both preconditions are on by default - chunking_advertise_hosts and
tls_advertise_hosts are each US"*" (src/src/globals.c:577 and :92) - each
advertised in the EHLO response behind a host check only
(src/src/smtp_in.c:4420 and 4434-4435), with no authentication involved. The
trigger is an ordinary dialogue:

    connect, EHLO, STARTTLS, EHLO, MAIL FROM, RCPT TO,
    BDAT <n>           sending fewer than <n> bytes of body,
    TLS close_notify   while leaving the TCP socket open

The unfinished chunk brings the server back for more body after the session it
was reading through has been destroyed. No credentials, configuration change or
race window are needed, and the attacker controls both the timing of the
teardown and the content then decoded into the released allocation. Outbound
delivery contexts are unaffected: tls_client_start() allocates no buffer.

The defect is present in the 4.100 development tree and, on the evidence of the
project's own release record, in all preceding releases that shipped the GnuTLS
backend with CHUNKING support: before the entry recording this fix,
doc/doc-txt/ChangeLog held no entry referencing the transfer buffer,
tls_close() or gnutls_record_recv(). The earliest affected release cannot be
established without external project history, which was not available.

CWE-416, Use After Free, is primary, with CWE-825, Expired Pointer Dereference,
for the destroyed session handle and CWE-672, Operation on a Resource after
Expiration or Release, for the transfer-state indices. Availability, integrity
and confidentiality are all affected. Any severity characterisation here is
code-derived, not verified against NVD, MITRE or any vendor advisory.

The OpenSSL backend is affected differently: the buffer use-after-free does not
arise there, that backend never releasing its transfer buffer; its equivalent
stale-reader path instead reaches a read call with a NULL session - CWE-476, a
crash of one forked process rather than heap corruption. What it does share is
the reading on in clear: its byte reader has the same fall-through, on the same
condition. No OpenSSL backend source is modified here. Both of those are
nonetheless closed, because the two corrections that close them - re-pointing
the saved reader vector, and deciding that nothing further is read - are made
in code the two backends share rather than in either of them.

================================================================================
REMEDIATION
================================================================================

Install a build containing the fix; no fixed release number is stated here.
Buffer, session handle and the callbacks operating on both are given one
jointly enforced lifetime.

-   At release the owning pointers are cleared, the water marks zeroed and the
    end-of-file and error latches set, for every teardown of a server session;
    and both sites that allocate a buffer initialise that state, so no later
    session inherits it.

-   What a server session records is dropped where each session starts, as its
    own state is set up and before its handshake, that being the one point
    every server session passes through: the server name the peer sent and
    whether it drives file expansion, the peer's certificate and ours, the peer
    DN and the session's cipher-suite string, the two verification results, the
    channel-binding type and the extended-master-secret record. The two
    certificates are library objects that context owns, and are released there
    rather than merely dropped, exactly once each. Only the credential cache is
    kept, that being what makes it a cache. What a finished session reported
    stays readable until the next one begins, the expansion variables and the
    logging of an accepted message depending on that.

-   The saved lower-layer reader vector no longer refers to the TLS readers
    once the buffer is released: it is re-pointed at the plain readers, and
    only where a vector was actually pushed, so the "nothing pushed" sentinel
    that push and pop key on keeps its meaning. The four chunked-body dispatch
    sites settle it the same way before they use it, as does the pop that writes
    a saved reader back as a top-level one - neither depending on which backend
    tore the session down. No path installs or dispatches a TLS reader
    afterwards, on either backend.

-   The input on the connection is ended at teardown, after the readers have
    been re-pointed and before the objects are released: it is recorded as
    ended and not read again, so a message in progress fails and no further
    command is taken. That holds wherever the session ended - in a transaction,
    a body transfer, an authentication exchange, a part-read command line,
    between commands - and for every teardown the server initiates itself. It
    is decided in the one refill every plain reader passes through as well, so
    a backend whose own teardown does not reach that point cannot read on
    either. A connection on which no session ever came up is left alone: a
    handshake that failed is answered as before, which matters because a
    handshake can fail late enough to have recorded a cipher suite, and because
    the server answers a failed one by reading on in clear to refuse until the
    peer gives up.

-   Every consumer of the buffer or the session tests for release before use
    and answers from that test: a reader that finds its session gone reports
    end of file, and does not fall back to the socket underneath. The one-byte
    write in shared code is guarded the same way, in a form correct for both
    backends, and the transplant paths hand sole ownership to the context that
    will close it. A session ending before its handshake completes is reported
    as a handshake failure, and its buffer and session released there.

Changes are confined to the TLS transfer-buffer lifetime logic and the
chunked-body handling: src/src/tls-gnu.c, src/src/tls.c, src/src/smtp_in.c, and
one added declaration in src/src/functions.h. There is no change to any public
API or ABI, to the SMTP protocol on the wire, to the spool file format, to any
configuration option or default value, or to the chunking state machine and its
transitions.

The one workaround is a compensating control, not a fix: restricting
chunking_advertise_hosts so CHUNKING is not advertised removes the trigger, at
the cost of an explicit configuration action and a standards-defined SMTP
capability, and it leaves the defect in the code. On security releases and
vendor backports see <https://wiki.exim.org/EximSecurity> and
<https://wiki.exim.org/SecurityReleaseProcess>.

--------------------------------------------------------------------------------
Behavioural Change
--------------------------------------------------------------------------------

Two consequences are worth stating plainly. A terminal 421 reporting the lost
connection still goes out, in clear, before the close: what is guaranteed is
about the read path, not that nothing at all is transmitted after teardown.

And a peer that ends a session meaning to go on using the socket is answered
with end of file. The smtp transport's hosts_noproxy_tls handoff is such a
peer: it shuts the session down and offers a fresh greeting in clear so that an
open connection can be handed to the next delivery, and that greeting is no
longer answered, so the connection is not handed on and the next message is
delivered on one of its own. No message is lost, deferred or duplicated by
that: what was delivered on the connection is logged as delivered, and what
remains is delivered afterwards. What changes is the re-use, and it shows in a
log as a connection per message - the marker recording a delivery made over a
handed-on connection is gone, the session-start sequence where that is logged
opens with a greeting of its own instead of resuming, and the receiving side
records the connection whose session ended as lost rather than closed by QUIT.

--------------------------------------------------------------------------------
Verification
--------------------------------------------------------------------------------

Remediation is checked two ways: a sanitizer build driven by a reproducer
combining a partial BDAT chunk with a TLS shutdown, and the project's
regression suite. The negative control is mandatory and ordered - the
reproducer must fail on the unremediated tree first and pass only after the fix
- and the pass criterion is the absence of any sanitizer report, not of a
crash.

Two of the unsafe paths are directly observable this way, and both were
observed. On the unremediated tree the reproducer yields a heap-use-after-free
WRITE of size 1 in tls_ungetc at src/src/tls.c:510 and a heap-use-after-free
READ of size 1 in tls_getc at src/src/tls-gnu.c:4027, both into one allocation,
released in tls_close (:3996, reached from tls_refill at :654) and allocated in
tls_server_start (:3279). The read becomes reachable only after the write has
moved the low-water mark, so seeing both requires a build compiled to recover
from an address error and run with halting on error off; a build without that
reports only the write. After the fix neither appears, not even from a build
that would have carried on past one.

Three things the sanitizer cannot show: the up-to-4096-byte store GnuTLS itself
performs into the released buffer, the allocation being Exim's but the write
executed inside an uninstrumented library; and the expired session handle and
the second release on the transplant path, which the reproducer does not drive.
All three are closed by the same change and argued from the code; no sanitizer
report is claimed for any of them.

The reproducer added to the suite drives one client session against a daemon of
its own, and it separates the two trees. It declares a chunk, sends all but one
byte of it, and then shuts the session down with the socket left open; the
server must answer with the terminal response and then be at end of file. Both
halves of that are asserted, and both are needed: unremediated, the server
reads on in clear, finds nothing there, and answers only when the receive
timeout expires - which is why the response is matched in full rather than by
its code, a loose match being satisfied by the timeout's own answer - and it
leaves the socket readable rather than ended. None of the runs recorded here
emitted the chunked-body double-push or double-pop diagnostic.

The two allocation sites initialise the transfer state belonging to the buffer
they allocate. On the transplant path that is structural: the context is copied
wholesale from an outbound connection and then given a buffer of its own, so
the state describing what it reads has to begin afresh against that buffer. At
the handshake site it keeps buffer and state allocated together; the successive
sessions on one connection that the code's own comment describes are no longer
reachable on the server path, teardown now ending the input, and no scenario in
the suite was found that fails when the two initialisations are removed - so
that item is stated here as structural correctness, not as a measured
regression.

The regression witnesses behave as before - chunked reception and transmission
with and without TLS, the state-transplant paths, signature verification, early
pipelining and per-recipient data. Six recorded outputs, across three tests,
change, and only for the re-use described above: each hands a connection on
after shutting its session down, and now uses a connection per message,
delivering the same messages. Those six were re-derived from observed output and
read line by line; nothing was accepted wholesale.

The whole automatic range was then run on each tree, and on each with both TLS
backends built: every test that fails on the remediated tree fails on the
unremediated one too, and none fails there that passes on it - with one
exception, a client-side debug transcript of which the suite keeps a single
saved copy. The two TLS client libraries do not close a session identically:
one of them absorbs the first bytes of a plaintext response while waiting for a
closing alert, so that copy matches one and not the other. Everything the
server records matches on both. The reproducer is in the remediated tree only,
which is what it is for.

================================================================================
STATUS AND IDENTIFIERS
================================================================================

No public identifier is asserted for this defect: no CVE identifier, severity
score, advisory reference or upstream revision identifier is claimed anywhere
in this report, no public record for it being retrievable when this was
written; any identifier found elsewhere in this source tree belongs to a
different, historical defect. By this project's own convention this directory
is named for the date the defect was raised, and an alias may be added if one
is assigned. The announcement is beside this report as oss-security.txt, the
chronology in the timeline file.
